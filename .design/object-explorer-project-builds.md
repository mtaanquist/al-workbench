# Object Explorer: compile project releases from Azure DevOps / GitHub

This document specifies a new Object Explorer ingest path: define a **Project**, point it at one or more Git repositories (Azure DevOps or GitHub), and have the workbench clone the source, resolve the right Business Central symbols, compile each extension, and ingest the resulting `.app` files as a `project`-kind Release. It is the compile-from-source sibling of the Microsoft-artifacts import documented in `object-explorer.md` ("Importing from Microsoft artifacts").

**Status:** **implemented and shipped** (PR-stack `feat/project-builds-*` → `feat/oe-project-build-polish`), validated end-to-end on staging. The sections below are the original proposal; **read "As built" first** for where the implementation diverged. The core property held: compiled `.app`s flow through the same `ReleaseImportService.ProcessReleaseAsync` every other source already uses — zero new ingest code.

> **Being superseded by the Artifacts tool — see `.design/artifacts.md`.** Projects and their builds are moving out of the Object Explorer into a dedicated Artifacts tool, with builds split off `OeRelease` into a first-class `OeProjectBuild` entity. Two parts of this document are already out of date as of the first Artifacts slice:
> - **Credentials are now per-user, not per-org.** The org-wide Azure DevOps/GitHub PATs on `organization_settings` are retired; each user stores their own token (`UserRepositoryToken`), and a build clones as the user who started it. `organization_settings` instead carries an admin-set *allowed providers* list. The "Credentials" section below describes the retired per-org model.
> - **Auto-build is removed.** Builds are user-initiated only (a background sweep has no user whose token to clone with), so `ProjectAutoBuildScheduler` and the remote-HEAD change detection are gone. `OeProject.AutoBuildEnabled` is slated for removal in the model slice.
>
> Object navigation is unchanged: an `OeProjectBuild` points at the `project`-kind `OeRelease` it produces, and the importer hook stays exactly as described here.
>
> **Kind restructure (post-Artifacts):** the `'project'` kind is now *reserved for pipeline-build Releases* — manual "Project-specific bundle" imports were merged into `'third_party'` (publisher differentiates them; migration `MergeProjectKindAndAddCal`), and the import forms can no longer post `kind=project`. The user-facing `/object-explorer` Third-party tab additionally surfaces each pipeline's latest ready build release — see the "Object Explorer split" exception in `artifacts.md`.

## As built

What shipped differs from the proposal in a few deliberate places; the rest landed as written.

- **Symbol country reuses `OrganizationSettings.AutoImportCountry`** — *not* a new `DefaultArtifactCountry` column. The fallback chain is per-Project `DefaultArtifactCountry` → org `AutoImportCountry` → `w1`. (Adding a separate column was deemed premature; the existing per-org country is the same concept.)
- **One artifact per build, not per extension.** `ProjectBuildService` resolves a single Microsoft artifact for the highest `application` Major.Minor across the discovered apps, extracts *every* MS `.app` from it (application + platform) into one package-cache dir, adds the repos' committed `.alpackages/` on top, then fetches whatever is still missing from Microsoft's public symbol feeds, then takes our own PTEs from the organisation's earlier builds (#901, see "Resolve symbols" below), and writes the stored uploads last. `alc` resolves each app's deps against that shared cache.
- **Parent import is inline, reusing the same download.** `ProjectBuildService.EnsureParentReleaseAsync` ingests the parent first-party Release *within the build* from the artifact zips it already downloaded for symbols — it does **not** call `ArtifactReleaseImporter.ImportAsync` (which would enqueue a second job). Best-effort: a failed parent import logs and the build continues with `ParentReleaseId = null`.
- **Build provenance captured.** `oe_project_build_results` carries `repo_url`, `commit_sha`, `commit_date` (per built app, read via `git show -s` right after clone) in addition to `(release_id, app_name, app_id, status, message)` — surfaced on the manage page and seeding a future Artifacts surface.
- **Build state lives in Status, and project labels aren't unique.** The provisional label is just the project name (final: `"{Project} on BC {Major}.{Minor}"`); the OE list/manage render an ingesting project release as **"Building…"**. Project-kind releases are **exempt from the unique label index** (`deleted_at IS NULL AND kind <> 'project'`) so a rebuild reuses the clean label — the release id is their identity. First-party label uniqueness (the artifact-sweep dedup backstop) is unchanged.
- **Admin UI is tabbed.** The admin Object Explorer is `Releases / Projects / Import` (`AdminObjectExplorerHeader`). Projects is a projects list → project detail page (`AdminProjectDetail`: build trigger, AL-compiler status/Update, repos via the ghost-row table editor, build history). The Import sub-nav dropped its Project pill.
- **User-facing Project tab is a project drill-in.** `/object-explorer` Project tab shows one card per project → click → that project's release cards (no hero). A project release shows its source repo URL(s) under the title.
- **Manual-symbols recovery shipped — as "persist + rebuild", not "recompile one extension".** The build report's "Supply missing symbols" action (shown for a project release with any `failed` row, partial or fully failed) uploads the missing dependency `.app`(s). They're stored at the *project* level in `oe_project_symbols` (org-scoped, `bytea`) — not transient, not per-extension — so `ProjectBuildService` merges them into the symbol cache (last — after the committed `.alpackages/`, the public symbol feeds and earlier builds, overwriting a stale copy; since #901 an app a stored upload carries is never fetched from a feed or taken from a build) on **this** build *and every later one*, including a future auto-build. The action then rebuilds the release in place via the existing `OeProjectBuild` retry path (`ReopenForRebuildAsync` accepts a `ready` partial as well as a `failed` release). This deliberately diverges from the original "re-compile just that one extension" proposal below: compiling one extension needs its sibling deps' symbols anyway (which aren't persisted), so a full rebuild — idempotent, and the same cost as the existing Retry — is both simpler and more useful than an isolated single-app recompile. Stored symbols are listed and removable on the project detail page. Retry-build (re-clone HEAD, rebuild in place) shipped earlier.
- **The symbol store is on the solution page, and a failure names what is missing (#901, Part 1).** The solution detail page has a manage-only **Symbols** tab (`ProjectDetailSymbols`, `/solutions/{id}?tab=symbols`) that lists the stored packages (file name, size, when added), uploads one or more `.app`s, and removes one behind a confirmation — the same `ProjectService` methods the admin action uses, so the fix no longer needs `/admin`. Uploading there does not rebuild; the consultant builds again from the pipeline. A compile that fails for a missing package gets a build-report message naming it: `alc` reports each one as `error AL1022: A package with publisher '…', name '…', and a version compatible with '…' could not be found…` (no file position, so the diagnostic parser never saw it); `AlcOutputParser.ParseMissingPackages` reads those lines and `MissingDependencyReport` turns them into "Missing dependency: *name* by *publisher*, version *x* or later (app id *…*). Looked in …", taking the app id from the extension's `app.json` by name. When the solution's environments report that app installed, it says which version the customer runs (production first) — read from the installed-apps mirror (`oe_environment_apps`), never from the tenant, so the build holds no customer credentials. When the solution has that app stored at a lower version (read from the stored package's own manifest), it says so too. A dependency on a sibling that failed earlier in the same build is reported as that instead — uploading would not help. The pipeline page's latest-build card now lists the extensions that did not build with their reasons (a partial build goes ready, so this was previously invisible there), and a missing-dependency row carries an **Upload symbols** link to the Symbols tab for anyone who can manage the solution; the admin manage page links there too.

## Why

Importing a project's solution into the Object Explorer today is a manual slog. An operator has to: clone each repo by hand; download the matching symbol packages from the project's BC environment; make sure the resource-exposure policy is set so the compiled output actually carries source; compile every extension in dependency order; zip the whole structure into the shape the importer expects; and upload it. Every step is a chance to get the symbol versions wrong or to drop source on the floor.

The Microsoft-artifacts import already proved the workbench can own this kind of fetch-and-ingest pipeline for *prebuilt* Microsoft releases. Project solutions are the missing half: the source lives in a repo, not on a CDN, and it has to be compiled before there's an `.app` to ingest. The version of symbols to compile against isn't a guess — each extension's `app.json` declares its `application` (and `platform`) version, which maps straight onto a Microsoft OnPrem artifact the workbench can already resolve and download (`BcArtifactService`). So the whole flow is mechanisable: clone → read `app.json` → resolve+download symbols → compile → ingest.

This graduates the roadmap item "Import a workspace straight from Azure DevOps (PAT)". It is adjacent to "Source-only ingest for uncompiled apps" but supersedes it for the case where we can compile: compiling produces a real `SymbolReference.json`, so we get full-fidelity ingest (resolved types, exact references) rather than the lower-fidelity header-scan path the source-only idea settled for.

## Scope

In scope:

- A **Project** entity that groups one or more repository URLs, managed from the Object Explorer admin surface much like the Artifacts tab manages countries/versions.
- **Per-org shared credentials**: one Azure DevOps Personal Access Token and one GitHub PAT per organisation, stored encrypted. Each repo names its provider; the build uses the matching org PAT.
- Cloning **HEAD of the default branch** of each repo (stated assumptions — no branch, tag, or commit selection in v1).
- **Per-extension symbol resolution** from each `app.json`'s `application` version via the existing Microsoft-artifact download, plus third-party dependency symbols sourced from a `.alpackages/` cache committed in the repo when present and, since #901, from Microsoft's public AppSource and Microsoft symbol feeds.
- **Compilation** with the BC Development Tools (`Microsoft.Dynamics.BusinessCentral.Development.Tools`, the `alc` compiler), in inter-app dependency order, emitting source into the output symbol package.
- Ingesting the compiled `.app`s into a `project`-kind Release whose parent is the matching Microsoft artifact Release (so cross-release reference resolution works unchanged).
- **Per-extension partial failure** with two recovery paths: retry the build, or manually supply the missing dependency symbols for a failed extension and re-run it. A failed extension never blocks its successful siblings.

Out of scope (v1):

- **Auto-loading the latest from a repo on a schedule.** A daily "rebuild every Project from HEAD" worker is a future nice-to-have (see "Future"), not v1.
- **Branch / tag / commit selection.** Always default branch, always HEAD.
- **Private NuGet symbol feeds.** *Reversed for the public feeds by #901, with the maintainer's sign-off:* third-party symbols now also come from Microsoft's public, anonymous `AppSourceSymbols` and `MSSymbols` feeds (see "Resolve symbols"). Still out of scope: any feed that needs credentials. A PTE nobody publishes comes from the organisation's own earlier builds when one of its solutions builds it (#901, Part 3), and otherwise from a committed `.app` or a stored upload.
- **Editing or persisting the cloned source as a workspace.** The clone is a transient build input, deleted after the build; only the compiled `.app` output is ingested.

## Credentials

Per-org shared PATs, stored exactly like the existing machine-translation API key:

- Two new nullable columns on `OrganizationSettings`: `AzureDevOpsPatEncrypted` and `GitHubPatEncrypted`, encrypted with the Data Protection key ring under a new purpose string on `OrganizationConfigService` (e.g. `GitRepositoryPatProtectionPurpose`), mirroring `MachineTranslationApiKeyEncrypted`. Losing the `app-keys` ring requires re-entering them. The audit interceptor redacts both ciphertext columns so they never land in history (same treatment as the SMTP password and the MT key).
- Administration grows a dedicated **Repositories** tab (`/admin/administration/repositories`, Admin-only) with a "Repository access" section: set or clear each PAT, with the view record exposing only `bool HasAzureDevOpsPat` / `bool HasGitHubPat` — never the plaintext. (A dedicated tab rather than sharing the machine-translation page: repo PATs are a distinct concern from translation, and the tab is the natural home for the per-org project-build settings that follow, e.g. the default artifact country.)
- Each Project repo declares its `provider` (`azure_devops` | `github`). The build picks the matching org PAT. A repo whose provider has no PAT configured fails that repo with a clear, recoverable message ("No GitHub PAT configured for this organisation — set one under Settings → Repository access") rather than a generic auth error.

The PAT is decrypted only inside the build service, only for the duration of the clone, and is injected as a transient credential (an `http.extraHeader` Authorization on the `git` invocation) — never written to disk, never logged, never put in the clone URL where it could leak into process listings.

## Project and repository entities

C# entities live in `Domain/Entities/ObjectExplorer/` alongside the other `oe_*` types; SQL tables take the `oe_` prefix; both are org-scoped via the standard `ScopeToOrganization<>` query filter (same shape as `OeArtifactVersion`).

```
Organization ──┐
               └── has many ──> Project  (table: oe_projects)
                                  ├── (organization_id, name, default_artifact_country?,
                                  │    created_at, updated_at, deleted_at)
                                  └── has many ──> ProjectRepository  (table: oe_project_repositories)
                                                     └── (project_id, provider, url, display_name)
```

- `oe_projects` — org-scoped, soft-deletable (`deleted_at`, consistent with the rest of the codebase). `name` is the project-facing label used to build the Release label. `default_artifact_country` is the optional per-Project country override described under "Symbol resolution".
- `oe_project_repositories` — a child table rather than a JSON column, because repos are listed, validated (per-provider URL shape), and managed individually. `provider` is a short enum string (`azure_devops` | `github`). One Project may span both providers.

The Release itself reuses the existing `oe_releases` schema (per `object-explorer.md`): `Kind = "project"`, `ProjectName` set from the Project's name, and `ParentReleaseId` pointing at the matching Microsoft artifact Release. No new Release columns. The build-result detail (below) is the only release-adjacent new table. Release label: `"{ProjectName} on BC {Major}.{Minor}"` — derived from the `application` version the apps compiled against.

## Build pipeline

The build is a new `ReleaseImportSource.ProjectBuild` job, drained by the existing `ReleaseImportWorker` alongside the `BcArtifact` case. A coordinator `ProjectReleaseImporter` (mirroring `ArtifactReleaseImporter`) creates the `ingesting` Release, captures the org identity, and enqueues the durable job (`PersistedImportJobs` + `ReleaseImportQueue`, so it survives a restart). The build logic lives in a new `ProjectBuildService` whose output is the `List<AppFileUpload>` the importer already consumes, plus a per-extension result list.

### 1. Clone

Shell out to `git`, following the external-process pattern `BackupService` uses for `pg_dump`/`pg_restore` (resolve the binary from a `GIT_PATH` env var, default to a PATH lookup). Clone HEAD of the default branch of each of the Project's repos into a temp directory under the OS temp path (mirroring the `oe-artifact-` / `oe-dvd-` temp-file convention), with the PAT injected as a transient `http.extraHeader`. Everything is deleted in a `finally` block exactly as `ReleaseImportWorker` cleans up staged zips and downloaded archives.

### 2. Discover apps

Walk each clone for `app.json` files (skipping `.alpackages/`, `.vscode/`, test-app folders by the same heuristics the workspace walker already applies). Each `app.json` is one extension to build. Read its `id`, `name`, `publisher`, `version`, `application` (and `platform`) version, and `dependencies`.

### 3. Resolve symbols (per extension)

- **Platform + foundational symbols** come from the `application` version via `BcArtifactService.ResolveOnPremAsync` + `DownloadArtifactSetAsync`, which already return the platform `System.app` plus the localized Base Application / Business Foundation apps. The **country** is resolved per-Project override → org `DefaultArtifactCountry` (a new `OrganizationSettings` column) → `w1`. A dedicated default is cleaner than reusing `AutoImportCountry`, because auto-import can be off while project builds are on.
- **Third-party dependency symbols** (`dependencies` in `app.json`) are assembled into the shared package cache from five sources, in this order:
  1. the Microsoft artifact above;
  2. a `.alpackages/` cache committed in the repo, when present (older repositories only — the platform `.gitignore` has always ignored it, and repositories are dropping it);
  3. **Microsoft's public symbol feeds** (#901) — `AlSymbolFeedResolver` looks up every dependency that is still missing, by app id: the `AppSourceSymbols` feed first, then `MSSymbols` for Microsoft apps the artifact did not carry;
  4. **the organisation's own earlier builds** (#901, Part 3) — a dependency on a PTE another solution's pipeline builds is resolved from the `.app` that solution's build retained (`oe_project_build_artifacts`, looked up by `app_id`), so solution A depending on solution B's extension builds with nothing committed and nothing uploaded;
  5. the operator's **stored uploads** (`oe_project_symbols`), written last so a same-named copy is overwritten — the upload is the deliberate override.

  An app counts as already supplied — and is never fetched — when an `.app` in the cache carries its id at or above the version asked for, when the build compiles it itself, or when a stored upload carries it (the uploads are read before the feeds and the earlier builds are consulted, for exactly this reason). So the precedence is upload, then feed, then earlier build.

  **Which earlier builds may supply a dependency — a static rule.** The build runs in a worker with an organisation scope and no person behind it, so `ProjectAccess` has nobody to answer for. An artifact is therefore a candidate only when its solution is **Public or Read-only** (everyone in the organisation may read those anyway) or is **the solution being built**; a **Private** solution's builds never resolve another solution's dependency. The lookup reads through the organisation's ordinary query filter — no `IgnoreQueryFilters()` — so another organisation's builds are never candidates either. Of the candidates, the build takes the highest version at or above the `app.json` floor (the newest build breaks a tie), from a `ready` build of a solution that is not deleted; a failed build, a pull-request check (its apps are unreviewed) and a build compiled against a newer Business Central than this one are passed over. What a resolved PTE itself depends on is followed the same way, and whatever no earlier build carries goes back to the feeds for a second look, so a PTE that depends on an AppSource app still compiles. The log names the source: "Resolved CRONUS Base 1.4.0.0 from solution Contoso's build #12." A row retained before `app_id` existed is stamped once from its own manifest by a startup pass (off the startup path, one organisation at a time under its own scope); until then it is simply not a candidate. The feed lookup follows the feeds as they actually behave (verified against the live feeds in #901): search by the app id GUID and read `data`, ignoring `totalHits` (the Azure DevOps search reports 0 while returning results) — never build the package id from publisher and name; follow the 303 the `.nupkg` answers with (redirects are followed by hand and must stay on HTTPS); sort the version index rather than read either end, since it runs newest first; take the `.app` from the package root and check its manifest carries the requested app id. Of the versions at or above the `app.json` floor, the build takes the newest whose nuspec says it was built against the build's Business Central Major.Minor or older — a vendor's newest release usually needs a newer base app than the build compiles against. Each package's nuspec names the apps it depends on by app id, and those are resolved the same way, so an AppSource app that depends on another AppSource app works (cycle-safe, capped per build). The Microsoft feed publishes one package per country plus a worldwide one for the same app; the build's country wins, else the worldwide one.

  Fetched packages are cached under `symbol-cache/{app id}/{version}/` inside the compiler's install root, so they ride on the existing `app-altool` volume (no Postgres, no new volume); a rebuild copies from there without a network call. The feed URLs are `AL_SYMBOLS_APPSOURCE_FEED` / `AL_SYMBOLS_MICROSOFT_FEED`, defaulting to Microsoft's feeds. The build log gains a **Symbols** section with one line per package ("Resolved Continia Core 29.0.0.199323 from the AppSource symbol feed.") and one per app no source had, naming the app id and the feeds tried.

  **Integrity: HTTPS, not the NuGet signature — a decided choice.** The feeds publish no package hash (the registration `catalogEntry` has no `packageHash`), so the SHA-512 check the compiler download does (#429) has nothing to compare against. The packages are NuGet-signed, but verifying `.signature.p7s` would make every build depend on the signing certificate chain and its revocation checks, for a file whose risk is lower than the compiler's: a symbols `.app` is compiler input, never a binary this process runs. So the build relies on HTTPS to the Microsoft-hosted feed, keeps the zip-slip guard (only a plain root-level file name is ever written), caps the extracted size, and refuses a package whose manifest names a different app than the one asked for.

  When a dependency's symbols can't be found anywhere — unreachable feed, unknown id, no version that fits — **only the extensions that need it fail**, at compile time, exactly as before; the resolver never throws into the build, and its siblings still build and ingest. (Concrete case from the request: a repo with `Core` and `ContiniaExts` where Continia's symbols are missing still imports `Core`.) A solution pinned to a Business Central older than a vendor's feed history (Continia Core's starts at 25.0) still needs the upload path.
- The matching Microsoft artifact Release becomes the new Release's `ParentReleaseId`. If that artifact Release isn't imported yet, the build imports it first by reusing `ArtifactReleaseImporter.ImportAsync` (auto-import the parent rather than refusing — see Open questions), so the chain is closed before the project apps land.

### 3b. Ingest the resolved symbols (#901, Part 4)

Once the parent Release is settled, every package the feeds resolved (fetched or from the cache) is put into the Object Explorer so our code's references into the vendor resolve instead of dead-ending at the vendor boundary:

- **Once per (app id, version), shared across builds.** Each package becomes its own `third_party` Release, labelled `<Name> <Version> (symbols)`, with the package's publisher and the dedup key `symbols:{app id}:{version}` — the same per-org, active-rows-only key the first-party artifacts use. A later build that resolves the same version finds it by that key and creates nothing. Its parent is the Microsoft Release this build resolved. Ingest reuses `ReleaseImportService.ProcessReleaseAsync` over one `AppFileUpload`, unchanged.
- **Linked, not parented.** The project Release gets one `oe_release_dependencies` row per vendor Release it resolved, and a rebuild replaces that set. The links are written when the build finalises the Release, *before* the compiled apps are ingested, because the ingest's call-site pass reads the chain. How the chain uses them is in `object-explorer.md` ("Dependency links").
- **Best-effort, like the parent.** A package that cannot be read, is not the one the feed supplied (a stored upload overwrote it), or fails to ingest is left unlinked with a line in the build log's Symbols section; the build carries on. A vendor Release whose earlier ingest failed is not linked until someone retries it from its manage page. A concurrent build winning the dedup-key insert is adopted, as for the parent (#431).
- **Where it shows.** The pipeline-build Release's manage page (`/admin/object-explorer/release/{id}/manage`) lists the vendor Releases it linked, each linking to the Release; the vendor Releases themselves appear on the Object Explorer's Third-party tab under their publisher.

A symbols-only Release has objects and signatures but no source, so go-to-definition on a vendor object from our code has nowhere to land (the viewer shows nothing for it, as for any source-less target) — find references, the Using panel and search are what it enables.

### 4. Compile

Topologically order the repo's apps by their inter-app `dependencies` and compile each with `alc` against the resolved symbol set. The compile requests **source embedded in the output symbol package** — this is the "resource-exposure policy correct" concern from the request made mechanical: the produced `.app` carries its `src/` tree, which the ingest pipeline prefers (per the Storage-policy table in `object-explorer.md`). Each produced `.app` becomes an `AppFileUpload`.

### 5. Ingest

The `AppFileUpload` list flows into the existing `ReleaseImportService.ProcessReleaseAsync` — **zero new ingest code**.

> **Design property: `AppFileUpload` is the common ingest currency.** Every release source — manual upload, DVD URL, Microsoft artifacts, and now project builds — converges on the same `List<AppFileUpload> → ProcessReleaseAsync` seam. The existing `ReleaseImportSource.BcArtifact` case already proves it (download → uploads → ingest). A future, richer source (a more elaborate artifact pipeline, a different VCS, a binary drop) plugs in by producing that list and adding a `ReleaseImportSource` variant; it never touches ingest code. Project builds compose with the artifact path directly — step 3 downloads Microsoft artifacts as the *symbol input* to the compile, then feeds the compiled output back through the same ingest.

## Partial failure, retry, and manual symbols

The error handling the request calls "critical" is per-extension, not per-build.

- A new `oe_project_build_results` table records one row per extension in a build: `(release_id, app_name, app_id, status, message)` with `status ∈ {compiled, ingested, failed}`. Successful `.app`s ingest normally; a failed extension leaves a row with a friendly reason — missing third-party symbols, a compile error, or a missing PAT.
- A Release with some failed extensions still goes **`ready`** (its successes are immediately usable) but carries a "partial" badge and a build-results panel on its manage page. We do not hide a half-good import behind `failed`.
- Two recovery actions on the manage page:
  - **Retry the build** — reuse the existing failed-release retry shape (`ReopenForRetryAsync` + re-enqueue), here re-enqueuing an `OeProjectBuild` job. Useful when the failure was transient (a flaky clone, a parent artifact that has since been imported).
  - **Manually supply symbols** — upload the missing dependency `.app`(s) for a failed extension, then rebuild. This is the "manually choose symbols" fallback: when a third-party dependency isn't in the repo's `.alpackages/`, on a Microsoft artifact, on the public symbol feeds, or in an earlier build of one of the organisation's shared solutions, the operator drops in the symbols they have and the build resolves. *(As built this persists the symbols against the project and rebuilds the whole release rather than recompiling a single extension — see the "Manual-symbols recovery shipped" note under "As built" for why.)*
- **A missing dependency is named, and the fix is on the solution.** A failed row for an unresolved dependency says which app (name, publisher, app id), the minimum version asked for, where the build looked, which version the customer's environment runs, and whether the solution already stores that app at an older version. The stored packages are managed on the solution's **Symbols** tab, which the failed build links to. See "The symbol store is on the solution page" under "As built".

### Building against the next version (#993)

A build can compile against the **next** Business Central version instead of the one the manifests ask for, so a breaking change in the Base Application shows up as a red build weeks before the customers' environments move. `ProjectBuildOptions.Target` is a `BcBuildTarget`: `Current` (the default, and exactly the path described above), `NextMinor` or `NextMajor`. The pipeline setting that chooses it, how it shows on the build and pipeline pages, and the rule that such a build cannot be deployed or tagged are #994.

- **Where the symbols come from.** Microsoft's insider storage (`BcArtifactIndex.InsiderCdnHost`, env `BC_INSIDER_CDN_HOST`) publishes the same per-country index as the released storage, anonymously, but only for the **sandbox** type. Its artifacts put every Microsoft app under `Extensions/` and `System.app` in the platform zip, which the artifact walker already reads. The Microsoft symbol NuGet feed carries no prereleases, so the artifact is the only source for next-version Microsoft symbols. `BcArtifactService.ResolveTargetAsync` picks the build with `BcArtifactIndex.SelectTargetVersion`, judged against the newest build the *released* index has shipped (never the wall clock): **NextMinor** is the newest build of the highest minor above the shipped one on the shipped major (28.6 while 28.5 has shipped); **NextMajor** is the newest build of the lowest minor of the *smallest* major above the shipped one (29.0 today, 30.0 once 29 ships). Smallest, not highest: 30.0 is already in the insider index while 29.0 is in preview, and it is not what "next" means to the team. When the insider index has nothing that fits, the build fails with "Microsoft has not published a preview of the next major Business Central version for country 'dk' yet."
- **The manifests are not rewritten.** The build compiles the repositories as they are against newer symbols; that is the whole point. Third-party symbols need nothing: the feed resolver takes the newest package built against the build's Major.Minor or older, so a 29.0 build gets today's AppSource packages. The resolved Major.Minor is what lands in `OeProjectBuild.BcVersion` and the release label ("CRONUS on BC 29.0"), and a **Build** log line names the insider build and the compiler it used.
- **The parent release is the catalogue's preview.** The build parents onto the same `bc-insider:{Major}.{Minor}:{cc}` release the daily preview sweep imports (`.design/object-explorer.md`, "Preview builds"), importing it inline when absent, so an organisation holds one preview per Major.Minor and country whichever of the two brought it in. The build refreshes it by the sweep's own rule: older than `PreviewRefreshAge` (14 days), a different insider build, and not mid-ingest, then the old one is soft-deleted and the current build imported in one transaction. That is the retention for insider artifacts; nothing is cached by full build number, because the symbols a build compiles against are downloaded fresh for every build anyway (about 1 GB for the country zip and 1 GB for the platform), and only the catalogue copy is shared. The sweep's supersede rule compares Major.Minor rather than major so a next-minor build's 28.6 preview survives while 28.5 is the newest shipped release, and goes once 28.6 ships.
- **A compiler per target.** `AlCompilerProvisioner` installs each version into `{AL_COMPILER_DIR}/{version}/` with its own `installed.json`; an install made before #993 (at the root) is moved under its version on first use, so nothing re-downloads on upgrade. `Current` and `NextMinor` use the stable line exactly as before (the pin, else the installed stable compiler, else the newest stable on NuGet). `NextMajor` reads the feed on every build and uses the newest **prerelease numbered above the newest stable release** (`PickPrereleaseCandidates`); the feed does not say which Business Central major a compiler serves, so "the newest beta ahead of stable" is the rule rather than a mapping, and when no beta is ahead of stable (a line has just shipped) the stable compiler is used. Installing a newer beta removes the older betas. `AL_COMPILER_VERSION` pins the stable line only; there is no pin for the beta.
- **Preview software.** Insider artifacts carry Microsoft's own EULA (`EULA.html` in every artifact). Nothing is accepted in-app, but the builds are compiled against pre-release software, and the build log names the preview build it used.

## Toolchain and deployment

The compile step needs `git` (added to the image) plus the AL compiler (`alc`). The compiler is **not** baked into the image — it's provisioned at runtime into a persistent volume so a new compiler version never requires an image rebuild.

**Compiler packaging (verified empirically, June 2026; re-verified September 2026 after #921).** The compiler is in the `Microsoft.Dynamics.BusinessCentral.Development.Tools` NuGet package as a **framework-dependent** `tools/<tfm>/any/alc.dll` (plus `altool.dll`), which the runtime image's own `dotnet` runs. Key facts found by testing:
  - **The `.Linux` package stopped carrying the compiler at 18.x.** Up to 17.x, `Microsoft.Dynamics.BusinessCentral.Development.Tools.Linux` shipped an apphost `lib/<tfm>/alc` (58 MB); from 18.0.41 it is 734 KB of code analyzers and nothing else, so a provisioner that took "the newest `.Linux` package" installed nothing runnable and every build failed with "compiler unavailable" (#921). The main package has `tools/net10.0/any/alc.dll` from 18.x and `tools/net8.0/any/alc.dll` at 17.x; `dotnet alc.dll /?` from 18.0.41.62505 prints `Microsoft (R) AL Compiler version 18.0.41.62505` and exits 0 on a .NET 10 host.
  - **`dotnet tool install` is still the wrong delivery** (microsoft/AL#8242): downloading the `.nupkg` (a zip) and extracting the folder flat is what works.
  - **`net10.0` first, roll-forward otherwise.** The provisioner prefers `tools/net10.0/any/` (runs natively on `aspnet:10.0`), else the highest `netN.0` with `DOTNET_ROLL_FORWARD=LatestMajor` scoped to the `alc` subprocess.
  - **The integrity hash comes from the registration catalog entry**, not the flat container: nuget.org answers 404 to `<package>.nupkg.sha512` for every package now (checked against `newtonsoft.json` too), which had turned the #429 check into "refuse every install". The provisioner now reads `registration5-gz-semver2/{id}/{version}.json` → `catalogEntry` → `packageHash` (SHA-512, base64; the resource is gzip-encoded), which is where the NuGet client reads it, and still refuses to install when the hash is missing or differs.
  - **Stable releases only by default.** The index ends in a `30.0.42.11883-beta`; a beta compiler is a choice an operator makes with `AL_COMPILER_VERSION`, so the default walk skips prereleases unless the feed holds nothing else. The one exception is a next-major build, which takes the newest beta ahead of stable into its own folder (see "Building against the next version").
  - **A package without a compiler is skipped, not installed.** With no `AL_COMPILER_VERSION` pin the provisioner walks the newest three stable versions, newest first, and takes the first whose package actually holds `alc.dll` (or a `lib/<tfm>/alc` apphost); a pinned version is tried alone. The marker file records the entry it installed, and volumes provisioned before #921 (marker without an entry, `bin/alc` apphost) keep running as they are - nothing re-downloads on upgrade.
  - The build invokes `dotnet <bin>/alc.dll ...` for a framework-dependent install and `<bin>/alc ...` for an apphost; `AlCompilerInfo.FileName` / `LeadingArguments` hide the difference.
  - `AL_COMPILER_PATH` overrides the resolved compiler for air-gapped installs (pre-seed the volume; an `alc.dll` path is run through `dotnet`, anything else directly); `GIT_PATH` resolves `git` (default PATH lookup), following the `BackupService` `pg_dump` pattern.
  - **Graceful degradation:** if NuGet is unreachable and the volume is empty, the Project-build feature reports itself unavailable with a clear message and the app still boots — the compiler isn't a hard startup dependency.

**Invocation.** Per-project `alc /project:<dir> /packagecachepath:<symbols> /out:<app>` in the build's own topological order (the dependency-ordering `al workspace compile` only exists in v17+ and isn't needed — per-project compile is required anyway to attribute per-app failures). Image change is just `apt-get install -y git`.
- **Graceful degradation when the toolchain is absent.** If `alc`/`git` can't be resolved (e.g. a custom image build that dropped them), the Project-build feature reports itself unavailable with a clear message and the app still boots — the compiler isn't a hard startup dependency the way the database is. (A `/healthz` signal for "build toolchain present" is optional and can wait.)
- **Memory.** The container's 4 GiB ceiling (`compose.yaml`) is already sized for heavy Object Explorer ingest. A compile plus a downloaded symbol set may push it; the operational note is to bump the reservation or stream the symbol cache to disk rather than hold it in memory. Recorded as an operational concern for the implementation, not a blocker.

### Architectural fences crossed (maintainer-approved)

Two fences from `CLAUDE.md` are deliberately crossed here, with sign-off:

1. **A background worker that compiles.** This is *not* the "synchronous generation" fence — that rule is about the workspace/extension generator, which stays synchronous and in-memory. The build worker is architecturally identical to the existing `ReleaseImportWorker` / `BackupScheduler` / `OffsiteRestoreWorker` (`BackgroundService` + durable queue + heartbeat). It's heavier (it shells out and compiles), but it's the same shape.
2. **`git` + `alc` baked into the image as a new build dependency.** New tooling in the container, accepted as the cost of owning the compile step.
3. **An outbound dependency on Microsoft's public symbol feeds** (#901). A build now reaches `dynamicssmb2.pkgs.visualstudio.com` for dependency symbols it was not handed. It reverses the v1 "no NuGet symbol feeds" line; the maintainer signed off in #901. It is a runtime nicety, not a hard dependency: an unreachable feed fails only the extensions that needed it, and everything already cached keeps working offline.

## MCP parity

Nothing new is required on the MCP surface. This is an admin/authoring flow; the *result* — a `project`-kind Release with its modules, objects, symbols, and references — is already exposed through the existing Object Explorer MCP tools (`list_releases`, `list_release_modules`, `find_references`, …). Per the `CLAUDE.md` rule, authoring flows that aren't part of the AL-reading surface skip MCP, and the read surface here is unchanged.

## Future

- **Auto-build scheduler.** ❌ *Removed* (see the note at the top of this file). It was designed as a daily sweep mirroring `ReleaseAutoImportScheduler`, opted into per project, probing each repo's remote HEAD with `git ls-remote` and queueing a build when a HEAD moved. It is gone: a background sweep has no user whose token to clone with. No such hosted service is registered and no env var configures one. Rebuilds are user-initiated from the project detail page. The rest of that design still holds — the `commit_sha` provenance is the dedup key, and because the label is display-only (see the dedup-hardening work in `roadmap.md`) a rebuild needs no SHA/date label suffix; the release id is its identity.

## Open questions

1. **Label / dedup when HEAD moves.** ~~A project build has no stable version key.~~ **Resolved:** the auto-build scheduler dedups on the captured per-repo `commit_sha` (skip when HEAD hasn't moved) and creates a new release per change. No label suffix is needed — the dedup-hardening work freed the label to be display-only, so the release id is each build's identity. See "Auto-build scheduler" under Future.
2. **Mixed-country repos.** Country is resolved per-Project → org default → `w1`. The remaining edge is a *single repo* whose apps target different localizations — unlikely in practice; note and defer rather than over-engineer.
3. **Compiler version selection.** ~~Single baked vs per-version.~~ **Resolved:** the compiler is provisioned at runtime from NuGet into a volume (not baked). What the code does (corrected in #993; an earlier note here claimed prerelease tracking and an admin Update affordance, neither of which was ever built): the stable line installs the newest *stable* package once and keeps it until `AL_COMPILER_VERSION` names another; there is no admin version-check or Update action. Since #993 each version sits in its own folder, so a next-major build can run the newest beta beside it (see "Building against the next version"). A new compiler version never needs an image rebuild; bounded-band compile failures still fall to the per-app partial-failure path. See Toolchain.
4. **Missing parent artifact.** ~~Auto-import vs refuse.~~ **Resolved:** auto-import the matching Microsoft artifact Release inline within the build worker, so the parent Release is `ready` before the project apps ingest.

## Verification

When the feature is implemented, coverage follows the patterns in `ALDevToolbox.Tests/`:

- `ProjectBuildServiceTests` — over a synthetic two-app repo (`Core` + `ContiniaExts`) where Continia's symbols are absent: assert `Core` compiles and ingests, `ContiniaExts` lands a `failed` build-result row with a missing-symbols message, and the Release goes `ready` with a partial badge.

End-to-end smoke (manual, after CI green): configure a GitHub PAT, create a Project pointing at a real two-extension repo, run the import, and confirm the Release appears with both extensions' objects browsable and cross-module references into the parent BC release resolving — plus a deliberately broken dependency to confirm the partial-failure path and the manual-symbol recovery.
